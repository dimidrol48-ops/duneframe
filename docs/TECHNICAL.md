# Technical notes

How the disassembly is organised, the build switches, the C interface and the test tools. See the [README](../README.md) for building and playing, and [HANDOFF.md](../HANDOFF.md) for history and plans.

## Generated vs. committed files

Committed are the tools, the disassembler configuration (`tools/disasm/config.py`, `names.py`), the C code (`src/c/`), hand-written assembly includes (`src/autoplay.inc`), emulator traces (`traces/`), asset metadata (`assets/manifest.json`, `assets/probe.json`) and docs.

Generated by `make setup` from `baserom.gen` (and `variants/wide.gen`), not committed:

- `src/*.s`, `src/*.inc` (except `autoplay.inc`), `src/files.txt`, `src/bin/`;
- `assets/gfx`, `assets/palettes`, `assets/sound`.

To change the assembly, change the generator's input (names, C replacements, hooks and patches in `config.py`) and run `make setup` again. The build is defined by tools + config + C + your ROM.

## The 480x464 build (`WIDE`)

The archive's `..._480x464.gen` is another build of the same source, not a patch. It is folded in as a build flag:

```sh
cp "DuneII_-_The_Battle_For_Arrakis_Full_Version_(R82c)_480x464.gen" variants/wide.gen   # only for check-wide
make wide && make check-wide     # build/wide/dune2.gen, identical to the original 480x464 ROM
make mod WIDE=1                  # modded 480x464 build
```

What differs:

- **Screen-size constants.** 320x224 becomes 480x464. These are written as `SCREEN_W`/`SCREEN_H` expressions (defined in `src/symbols.inc`).
- **Layout values.** A few buffer masks and layout values change; these are 93 `.if WIDE` blocks.
- **Extra display code.** A new HBlank handler and extra VDP register writes in VBlank.
- **Code size.** The code grows 0xD0 bytes. Everything from 0x23480 (data, graphics, sound) is identical.

Real hardware and stock emulators can't show 480x464; the ROM needs the hack's modified Mednafen or Genesis Plus GX builds. At start-up it checks for them (`MegaCD_Detect`: a self-modifying-code prefetch probe and a VRAM write at 0x10000, i.e. 128 KB VRAM) and otherwise shows "Resolution 480x464 is not supported".

Testing the 480x464 builds:

- **In the patched Mednafen** (Windows build, run under wine + Xvfb by `tools/med/medrun.py`) with `AUTOPLAY=1` builds, which carry their input script (see Testing tools).
- **In the test harness** with `TESTHW=1`: two hooks make the emulator check pass on stock Genesis Plus GX. The picture is wrong without 128 KB VRAM, but the game logic runs, so lockstep comparisons and the mouse bot work.

Variant-only data and immediates the variant analysis missed are folded as raw bytes; `variant.py` then rewrites every 32-bit value in them that is a label address of the 480x464 build as `.long label` (when the 320x224 side of the block is a pointer table) and checks that the 480x464 ROM stays byte-identical (61 pointers; `tools/wide_rawptrs.py` lists what is left). Without that, the C and mod builds of 480x464 crashed at mission start: they move code, and those pointers did not follow.

How it was folded (`tools/disasm/variant.py`, run after `generate.py`):

1. Functions are matched by masked byte patterns.
2. The emulator traces are mapped onto the variant, and the variant is disassembled with labels named after base addresses.
3. The two generated trees are merged as `.if WIDE` blocks.

A second build of the same source is also ground truth for pointer detection. `tools/variant_ptrcheck.py` found 39 data pointers and 6 immediates the heuristics had missed, and 2 false positives, all fixed in `config.py`.

## Layout

| path | contents |
|---|---|
| `src/main.s` | Master file. It includes the 60 modules in ROM order, and they are assembled as one unit. |
| `src/code_XXXXXX.s`, `src/data_XXXXXX.s` | Code and data, split at data islands. The name is the original ROM address. |
| `src/symbols.inc` | Names for RAM variables and hardware registers. |
| `src/c/` | Decompiled C (`math.c`, `sound.c`, `anim.c`, `objects.c`, `misc.c`, ...), the mouse / multi-select mods (`input.c`, `group.c`) and `dune2.h` (types, ABI notes). |
| `src/c_interface.inc` | Assembly symbols exported to C, as `<label>_asm`. |
| `assets/gfx/*.png` | 111 tile sheets as 4bpp indexed PNGs using the in-game palettes. 2 of them are LCW-compressed in ROM and recompressed on build. |
| `assets/palettes/*.pal` | Palettes as text (Genesis BGR values). |
| `assets/sound/` | GEMS driver data: patches, envelopes, sequences, the Z80 driver, and the sample banks. The banks are split into per-sample `.wav` files. |
| `assets/manifest.json` | Where each asset lives in ROM and how to rebuild it. |
| `tools/` | Disassembler, asset tools, emulator harness and tests (see below). |

In the sources:

- Functions that have been identified are named (`VBlankHandler`, `Lcw_Decompress`, `Sound_PlayFx`, `Map_GetCell`, …; see `tools/disasm/names.py`).
- The rest are `sub_XXXXXX`, `loc_XXXXXX` and `dat_XXXXXX`, named after their original address.
- RAM variables are `g_*` when named and `ram_XXXX` otherwise.

## Editing

- **Code and data.** Edit `src/*.s` as normal assembly.
  - All references are symbolic: pointers in tables, jump tables, PC-relative tables and "tagged" pointers such as the vector table's `label+0xNN000000`.
  - Inserting or removing bytes anywhere is safe. Keep code on even addresses.
- **Graphics.** Edit the PNGs and keep the size and palette indices. `make` repacks them and recompresses LCW sheets.
- **Samples.** Replace a `.wav` with the same format. The GEMS bank headers are rewritten if sizes change.
- **Build switches.** These are assembler symbols. `make mod` sets the first two; `make nonmatching` sets only the first.
  - `NONMATCHING=1`: routines that have a C version jump to it. The C code is linked at the end of the ROM.
  - `MODS=1`: the mouse and multi-select: the code hooks in `MOD_HOOKS` (`tools/disasm/config.py`).
    - A hook overwrites instructions with same-size code that jumps to a trampoline at the ROM end, so nothing in ROM moves.
    - `tools/check_layout.py` verifies this.
  - `WIDE=1`: the 480x464 build.
  - Test builds only: `AUTOPLAY=1` (input script in the ROM), `TESTHW=1` (480x464 build on stock emulators), `TEXTMODS=1` (below).

### `TEXTMODS`

Small visible text changes that move every later address, to prove the build can be relocated (`MOD_PATCHES` in `config.py`). They are not in the playable builds.

| screen | original | mod | shift |

## Playing the mod ROM

`make mod` gives `build/mod/dune2.gen`; `make mod WIDE=1` gives the 480x464 version.

**Emulator (Windows).**

- **RetroArch** with Genesis Plus GX (for 480x464: the hack author's patched core, "480x464 & overclocked", linked from the hack's readme). Mouse: Quick Menu → Controls → Port 2 → Device Type = **MD Mouse**; Port 1 stays a 6-button pad. Toggle *Game Focus* (Scroll Lock) so RetroArch hands the mouse to the game.
- **Mednafen 0.9.48.0.H6** (the hack's patched build, also linked from its readme), which is what the 480x464 builds were tested with: `mednafen -md.screen_x 480 -md.screen256_x 480 -md.screen_y 464 -md.overclock 7 -md.input.port2 megamouse ROM`.

**Mouse** (Sega Mouse on port 2, read at the end of every pad read):

| mouse | action |
|---|---|
| move | moves the cursor (the centre of the bracket is the hot spot); near a screen edge the view scrolls, as with the pad |
| left click | A (select / order) |
| left drag | box select |
| right | B (cancel / deselect) |
| middle | C |
| start button | START (in RetroArch GPGX the middle button is START and the wheel is C) |

In menus, building placement and other screens without the free cursor, mouse movement steps the d-pad (one step per 24 pixels; at most one step is kept in hand, so the cursor stops when the mouse stops).

**Multi-select** (selection model on top of the game's single selection, `src/c/group.c`):

| input | selects |
|---|---|
| mouse drag, or hold Y, move the cursor, release Y | a box |
| A twice on a unit | all your units of that type on screen |
| A three times | all your combat units, or all harvesters/MCVs, on screen |

- Selected units show corner brackets.
- An order goes to the whole group. It runs the game's own order code once per unit, so each unit gets exactly its own order (harvesters harvest, attackers attack, ...).
- Move orders spread the units into a small formation.
- The group stays selected after an order (like the *No Cancel* control option).
- Clicking one of your units selects it alone; B deselects.

## C code

The C code is plain C with 32-bit `int`; use exact-width types (`s16`, `u16`, ...) for anything shared with the game.

The original code was built with a 16-bit-int compiler:

- arguments are pushed as words or longs, and the caller pops them;
- the result is in d0, or in a0 for pointers;
- d0-d2/a0-a1 are scratch.

The generator builds adapters from the C prototypes (`tools/disasm/csig.py`):

- `ret name(args) C_IMPL(label);` replaces an original routine.
  - With `NONMATCHING=1` the routine keeps its size (a `jmp` plus `nop` padding), so nothing else in ROM moves (low ROM is layout-sensitive).
  - It jumps to a stub linked with the C code, which repacks the arguments into 4-byte slots.
  - The stub also preserves d1-d2/a0-a1. Hand-written callers rely on registers the original leaves alone, e.g. `Math_DistanceArgs` keeps its return address in a0, and AI code keeps data in the upper word of d1.
- Some callers use registers the original leaves *changed*. `tools/check_regouts.py` finds them statically: it follows every call site of every C routine, in both builds, through control flow and callees, and reports registers read after the call that the stub does not reproduce. Found so far:
  - `VDP_SetPlaneA/B`: 480x464-only code ORs the 128K-VRAM bit into d1, the register value the routine wrote.
  - `sub_01E212`: the asm routine `sub_012EE2` borrows d3 and leaves bits in its upper word; the caller then uses d3 as an effect's position (a quirk of the original, kept).
  - Such routines list the registers in `C_REGOUT` (and `C_REGIN` for values they need from the caller); the C code passes them through `g_cRegOut` / `g_cRegIn`.
- `extern ret name(args) ASM(label);` is an original routine called from C, through a thunk that repacks the arguments back.
- Register-argument helpers (`Map_GetCell`, `Unit_GetByIndex`, `Sprite_Create`, `VDP_QueueDma`, ...) are inline-asm wrappers in `dune2.h`.

`C_FUNCS` / `C_EXPORTS` in `tools/disasm/config.py` list what is replaced and what is exported. `tools/disasm/classify.py` sorts all functions into compiled C (the decompilation candidates) and hand-written assembly.

**Tests.** Every C function is checked two ways:

- `tools/ctest/snaptest.py` runs the original (`baserom.gen`) and the C build (`make nonmatching`: C without mods, same layout) in Unicorn from **real game states**. Those states are registers plus all of RAM, captured at the function's entry by the tracing emulator while it replays a pool of save states (`tools/ctest/states.py`).
  - Compared: the result, all RAM outside the stack, the sequence of I/O writes, and every 16-bit register half the original leaves untouched.
- `tools/ctest/equiv.py` does the same on random inputs for small leaf functions.

- **Equal-timing lockstep** (`tools/lockstep.py --equal-timing`, `tools/lockstep_sweep.py`): the original and the C build run side by side and work RAM is compared every 10 frames. The test emulator makes the C code and the replaced routines' original bodies take no CPU time, so the two builds run on identical cycles and must match exactly. Result: all 47 scenarios (up to 18 minutes of play) identical for both the 320x224 and the 480x464 builds; this is what found the `sub_01E212` d3 quirk. The same check, original vs mod build with pad input (no Y), shows the mods leave the game untouched when not used.

## Regenerating the sources (what `make setup` runs)

`src/` is generated from the ROM plus emulator traces:

```sh
python3 tools/disasm/generate.py baserom.gen traces/merged.npz src      # src/*.s
python3 tools/assets/extract.py                                         # assets/
python3 tools/disasm/variant.py baserom.gen traces/merged.npz variants/wide.gen WIDE src   # fold in 480x464
make check check-wide
```

- Names, C functions, mods and file splits come from `tools/disasm/config.py` and `names.py`. Add names there, never in `src/`.
- The generator checks every instruction it emits. Encodings GNU as would "optimize" are written as raw words with symbolic operands.

## Known limitations

- **Timing.** The random number generator is deterministic (seeded once, advanced only by game code), but the game's pacing follows real time (VBlanks), so anything that changes CPU speed (overclocking, or the slower C code) changes when things happen and the games drift apart after a while. Same ROM, same input, same emulator settings: identical replay. The equal-timing lockstep removes this for testing.
- **Original bugs that depend on layout.** The original reads through null pointers (it hits the vector table) and uses RAM short addresses as long pointers (it reads ROM around `0xE3A8`–`0xF000`). Moving that low area changes behavior. Shift tests therefore insert padding above `0x10000`.
- **Unexplored code.** Code reached only by paths the scenarios never ran is disassembled statically, and pointers in data read only there are found by heuristics. The shift suite covers all major game modes.
